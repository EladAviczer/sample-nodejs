# CI Routing by Changed Paths and Branch

## Context and Problem Statement

The single `ci.yml` workflow used trigger-level `paths` filters that covered only `app.js`, `package*.json`, `Dockerfile`, `helm/**`, and `.github/workflows/**`. Terraform and ArgoCD changes ran no checks. The release chain used a separate `gate-code-change` job that recomputed the same app-code diff already needed for routing, duplicating logic. Branch behavior was implicit in the event triggers rather than explicit in the run.

## Decision Drivers

* Route on both changed file area and branch class (PR/main verify vs `v*` release)
* Reuse the existing app, Helm, and release jobs without breaking their behavior
* Keep deterministic logic in scripts, not in model-driven decisions
* Add new routed areas without adding new workflow files
* Preserve least-privilege permissions and concurrency groups

## Considered Options

* Single router workflow with a `detect` job that emits area and branch-class outputs
* Separate path-filtered workflow files per area
* Thin dispatcher calling versioned reusable workflows

## Decision Outcome

Chosen option: "Single router workflow with a `detect` job", because one run exposes the full routing matrix, outputs are deterministic shell results, and areas are added by extending one classifier rather than duplicating triggers.

The `detect` job computes a diff range from the branch class (PR: base ref merge-base; push: `HEAD^`; tag: previous semver tag) and emits `app`, `helm`, `terraform`, `argocd`, `verify`, and `release` outputs. Every downstream job declares `needs: detect` and gates on those outputs. Trigger-level `paths` filters are removed so the router always sees the change set.

### Consequences

* Good, because app, Helm, Terraform, and ArgoCD changes each run only their relevant jobs
* Good, because the release gate is now the same classifier used for verify routing — one source of truth
* Good, because branch context is passed through environment variables, not interpolated into shell source
* Bad, because every PR/main push starts the `detect` job even when no routed area changed
* Bad, because changes limited to `.github/workflows/**` trigger no downstream job
* Bad, because the diff base for PRs depends on `github.base_ref` being present and fetchable

### Confirmation

`actionlint` passes on `ci.yml`. Simulated PR, push, and tag runs of the classifier emit the expected area outputs. `helm lint --strict`, `terraform fmt -check` + `terraform validate`, and the ArgoCD YAML structure check pass locally.

## Pros and Cons of the Options

### Single router workflow with a detect job
* Good, because one run and one output contract make the routing matrix inspectable
* Bad, because the classifier script must handle first-commit and no-previous-tag cases

### Separate path-filtered workflow files
* Good, because each file is small and triggers are native GitHub syntax
* Bad, because the same trigger logic is duplicated and the full matrix is spread across files

### Thin dispatcher calling reusable workflows
* Good, because it scales to many repositories with versioned components
* Bad, because it adds indirection for a single-repository project

## Constitution Alignment

| Principle | Alignment | Notes |
|-----------|-----------|-------|
| Appropriate Delegation | ✅ | Routing is deterministic shell logic, not an LLM decision |
| Simplicity First | ✅ | One workflow, one classifier, no new workflow files |
| Build for Observability | ✅ | Classifier prints the changed file list into the job log |
| Security by Default | ✅ | Branch values passed via `env`, global permissions remain read-only |
