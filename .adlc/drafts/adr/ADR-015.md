# Terraform Plan in the PR Gate via OIDC Read Policy

## Context and Problem Statement

The `check-terraform` job routed from `terraform/**` changes ran `fmt -check`, `init -backend=false`, and `validate` only. It did not show the infrastructure diff that a merge would produce. Adding `terraform plan` requires AWS credentials for the provider and the `aws_vpc` / `aws_subnets` data sources. The repository has no remote backend and `terraform.tfstate` is gitignored, so CI plans against empty state and reports all managed resources as new.

## Decision Drivers

* Show the planned infrastructure diff when Terraform files change in a PR
* Use OIDC only — no long-lived AWS keys in repository secrets
* Reuse the existing `AWS_ROLE_TO_ASSUME` secret and `github-actions-refael` role
* Keep the PR job permissions minimal beyond the existing global default

## Considered Options

* OIDC via the existing release role, extended with a read-only inline policy
* A separate read-only OIDC role provisioned for plan, with a new secret
* Config-only checks (`validate` + `fmt`) without a real plan

## Decision Outcome

Chosen option: "OIDC via the existing release role, extended with a read-only inline policy", because it reuses the configured trust relationship and secret while granting only the Describe/Get actions the plan needs.

`check-terraform` elevates to `id-token: write`, calls `configure-aws-credentials` with `secrets.AWS_ROLE_TO_ASSUME`, and runs `terraform plan -input=false -no-color`. `terraform/main.tf` adds a `plan-read` inline policy to `aws_iam_role.github_actions` covering EC2 VPC/subnet describes, ECR/EKS describes, STS identity, and IAM role/OIDC-provider reads.

### Consequences

* Good, because PRs touching Terraform now show the actual config diff
* Good, because no new credential or secret is introduced
* Bad, because the release role gains read permissions in addition to ECR push
* Bad, because fork PRs cannot access the secret and will fail at the OIDC step
* Bad, because CI has no state file, so the plan shows all resources as additions

### Confirmation

`actionlint` passes. `terraform fmt -check`, `terraform validate`, and the local CI checks pass. The PR job is gated on `needs.detect.outputs.terraform == 'true'`.

## Pros and Cons of the Options

### OIDC via existing role with read policy
* Good, because setup is small and uses the existing trust relationship
* Bad, because one role now serves both push and plan duties

### Separate read-only plan role
* Good, because duties and blast radius stay separate
* Bad, because it requires new infrastructure and a new repository secret

### Config-only checks
* Good, because no AWS access is needed
* Bad, because no infrastructure diff is produced

## Constitution Alignment

| Principle | Alignment | Notes |
|-----------|-----------|-------|
| Security by Default | ✅ | OIDC only; inline policy is scoped to Describe/Get actions |
| Least Privilege | ✅ | No apply permissions granted to the PR job |
| Build for Observability | ✅ | Plan output is printed in the PR job log |
